# Changelog

KINO has no published release yet. Changes intended for the first release collect under **Unreleased**. Git remains the record for work completed before this file existed.

## Unreleased

### Changed

- **A four-camera capture no longer loses its largest frame to a retry stall.** The four-camera transport bench (2026-09-02, #132) found 6 of 20 grouped sets short a frame: under four concurrent transfers the RX FIFO drops the tail of a READ chunk near the 8192-byte boundary (the historical offset-8192 loss, no hardware flow control), and each loss waited out the full 1000 ms per-chunk timeout before a retry that then succeeded - enough 1000 ms stalls on cam2's ~458 KB frame to blow the 8000 ms whole-frame budget at 98%. `CHUNK_READ_TIMEOUT_MS` 1000 -> 400 (a healthy chunk arrives in ~120 ms, so a lost tail costs 400 ms to retry) and `XFER_BUDGET_MS` 8000 -> 12000 (room for the largest frame under four-way load), with a static assert tying them together. Nodes untouched; retry, CRC, mutexes, stacks and scheduler unchanged. Rerun: 20/20 complete, 0 lost frames. The offset-8192 tail loss is reproduced under load, not fixed - only made cheap to recover. (`firmware/HARDWARE_VALIDATION.md`, "One shutter, four frames".)

- **The bench capture command reaches all four camera channels.** `CAMERA_TEST` was the last cam1-only door: `run_capture()` now takes the channel and uses the per-channel link calls end to end, the stored frame is `C<n>.JPG` in its own TC folder, the reply names the cam it measured, and `CAMERA_LINK_STATS(_RESET)` lose the Milestone 1B gate and answer for the asked channel. Diagnostic surface only; the product capture path is untouched. With it, the basic four-camera hardware proof ran on the bench 2026-09-02: all four nodes individually and together, three matching checksums per frame, zero link errors (`firmware/HARDWARE_VALIDATION.md`, "Four nodes on four wires", #159).

- **Firmware 0.4.9: the settings do what they say.** Seven settings the camera stored, Studio drew a control for and the firmware then ignored (found 2026-08-30 while landing 0.4.8, issues #144 and #145). `shoot.previewQuality` never reached `viewfinder.c` and now picks the preview request, so low and high differ in frame bytes. `shoot.displayAfterShotS = -1` means "hold until dismissed"; `ui.c` multiplied it into a negative deadline, so HOLD behaved exactly like OFF, and the result screen now stays until a touch or a press. `body.sounds.warning` had no tone behind it and now plays one on a failed capture and on a full card. Favouriting worked over KDP and was stamped into `META.JSON`, but the body's own photo screen offered only DELETE and ROLL — it has FAVOURITE now, gallery tiles mark it, and `MEDIA_INFO` reads back the flag a thumb flipped. SETTINGS → DISPLAY gained rows for after-shot (0 / 1 / 2 / 3 S / HOLD) and camera-bank idle timeout, both of which were in config with no way to reach them from the body. `body.name` is new: a string of 0..24 characters, default `""`, shown on the About screen, written with `SET_CONFIG` like every other body field, and edited on Studio's Device page beside the serial — `config.device` is still the serial and still the identifier. And `GET_CAPABILITIES` gains `brightnessControl`, `false` on D4-V1, because `body.brightness` cannot ever work here: the Guition carrier drives the backlight from a plain GPIO and lit or dark are the only states (contract D11). Studio greys the slider on an explicit `false` and leaves it live on an absent flag, because firmware older than 0.4.9 never answered the question and a missing flag is not a no.

  **Per-camera exposure and gain reach a sensor for the first time.** QUAD slots have carried `exposureBias` and `gain` since the config schema existed and every look has a capture block, and none of it went anywhere: the node link had commands for quality and resolution only, and `capture.c` sent neither slot nor look values. `NL_CMD_SENSOR` (`0x15`) is the node-link command that closes it — `{aeLevel, gainCeiling, denoise, sharpness, quality?}` out, `{ok, applied:{…}}` back, with the node clamping to the driver's ranges and reporting what it actually set. It is node link, not KDP: no KDP command, payload or capability changed, and a host written against 0.4.8 needs nothing. Before each capture the P4 builds one request per camera in a fixed order — mode defaults, then the active look's capture block, then the QUAD slot's `exposureBias` and `gain`, the per-camera control winning over the shared one. `exposureBias` is an EV in -2..+2 and `set_ae_level()` takes an integer -2..2, so the EV rounds to the nearest step and -1.5 EV and -1.4 EV reach the same sensor; `gain` maps `auto` to AGC untouched, `low` to a 4x gain ceiling and `high` to 32x. Both mappings are pure C and host-tested. `META.JSON` records the echoed values per frame under `sensor`, so a photograph says what the sensor was told rather than what the config held at some later moment; `quality` there is the sensor's 5..63 scale, not the 60..95 wire percentage, the D12 conversion happening before the link.

  A sensor apply that NACKs or times out is logged and the trigger goes out anyway, with `sensor` omitted for that frame — a missed photograph is the wrong price for a settings write. So an absent `sensor` block has two causes, older firmware or a refused apply, and neither means the frame is bad. What still does not happen: the rest of a look — contrast, saturation, temperature and the other grading fields — stays Studio's at import, no grading runs on the camera, and `colorMode: 'mono'` is still not applied on the body. The slot stores mono, `META.JSON` carries it, and the conversion happens at import; that one is a product decision still open, not an oversight. Contract D19 records the command, the merge order, the two mappings, the failure rule, `brightnessControl` and `body.name`. The node image is built from the same `firmware/VERSION`, so a camera node reports 0.4.9 too.

  The P4 gets its own partition table. `CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE` gave a 24 KB NVS, one 1500 KB `factory` slot and no OTA, and left about 12 MB of the 16 MB part unaddressed; at 0.4.8 the radio image measured 1451 KB in that slot, 3 percent free, and the next radio feature did not fit. `firmware/p4/partitions.csv` replaces it with two 3 MB OTA slots sized for the radio image plus real growth, a 256 KB NVS, `otadata`, `phy_init`, a 64 KB coredump partition, and 9.6 MB left unallocated for a future on-device data partition. `ota_0` starts at 0x10000, where `factory` did, so an image built before this change still flashes and boots there. The panic handler now writes to the coredump partition (`CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH`), which costs 21 KB on both images: default 864 KB (0xd8110), radio 1472 KB (0x1702b0) with the new table. The CI size guards are re-derived from the 3072 KB slot, 1200 KB and 1600 KB. Flashing the new table erases NVS - config, hwv rows, saved Wi-Fi networks and the Roll device credential - so no unit carries it yet; `firmware/README.md` has the sequence and what restores what.


- **Firmware 0.4.8: the camera holds looks and sounds.** Ten commands answered `UNSUPPORTED_COMMAND` while Studio's Looks, Wiggle, Quad and Device pages, its backup and restore, and the reference mock all spoke them, and the camera's own LOOK tab offered COLOUR / B&W out of config. `GET_RECIPES`, `SET_RECIPE`, `UPLOAD_RECIPE` and `DELETE_RECIPE` answer now, and so do `GET_SOUNDS`, `SOUND_BEGIN`, `SOUND_CHUNK`, `SOUND_END`, `SOUND_READ` and `SOUND_DELETE`, with the request and response shapes `MockKinoDevice.ts` has always given — a host written against the mock needed no change. Eleven factory looks are compiled into the image from `firmware/p4/main/factory_recipes.json`, which is the same eleven documents as `FACTORY_RECIPES` in `packages/test-fixtures`; two copies of one document is how a Party Neg on the bench stops being the Party Neg in the app, so `factoryRecipeParity.test.ts` compares them id by id and editing one alone is a red test rather than a picture nobody can explain. Custom looks live on the card as `/sdcard/KINO/RECIPES/<id>.json` and custom clips as `/sdcard/KINO/SOUNDS/<id>.wav`; each upload is written to a temporary file and renamed at the end, so a power cut mid-transfer leaves nothing half-written.

  `SET_RECIPE` takes an optional `cam` — absent writes `wiggle.recipeId` as before, `cam1`..`cam4` write one quad slot, `all` writes all four and wiggle — and refuses an id that is on neither the factory nor the custom list, because a config naming a look the device does not have renders as the wrong picture at import rather than as an error. `GET_CAPABILITIES` grows `recipes` and turns `customSounds` true; both come off the same predicates the dispatcher gates on, so the flag and the handler cannot disagree. `recipes` is optional in `Capabilities`: firmware older than 0.4.8 omits it, and an absent flag means the commands NACK, not that the answer is unknown. `SOUND_END` adds one refusal the mock does not have — `BAD_FORMAT` for anything that is not 16 kHz mono 16-bit PCM — because the playback path has one sample rate and no converter, and a clip that fails there would otherwise fail at a shutter press instead of at upload. Limits are the mock's: eight clips, 128 KB each, 8192-byte chunks.

  What the camera still does not do is grade. No look's capture block reaches a sensor register; a look is stored, selected, carried in `META.JSON` and applied at import, exactly as before. Contract D17 drops from 27 unimplemented commands to 17, D18 records the `cam` field, `BAD_FORMAT`, the parity rule and the card paths, and Studio's conformance suite is 33 cases with `GET_RECIPES` passing and a new read-only `GET_SOUNDS` beside it.

  Found on the bench while proving it: **every KDP reply over about 4 KB had been silently lost since the first firmware.** `usb_link_write()` handed a whole frame to `usb_serial_jtag_write_bytes()`, which copies the request into the driver's 4096-byte TX ring as one item; an item larger than the ring can never fit, the call returned 0 at once, and the loop read that as "host gone" and dropped the frame. Everything under 4 KB worked, which is why `GET_HW_VALIDATION` at 3.8 KB answered and `GET_LOGS` never did - the trap in the bench notes that read "4 KiB frames time out". Writes go to the driver in 1024-byte slices now; `GET_LOGS` answers 14 KB on the wire and `GET_RECIPES` was the command that finally made it visible. The console log still shares that USB port, which is what a host decoder's `discardedBytes` are.

- **Firmware 0.4.7 / hardware 0.1.3: the shutter has a pin.** `BOARD_BTN_SHUTTER` has been `BOARD_BTN_NONE` since the first image and every capture has been fired from the touch screen, which works at a bench and is not a camera. It takes `GPIO28`, JP1 pin 21 — the pin ECN-0002 gave to `FLASH_EN`. The other two candidates were rejected on the board, not on preference: `GPIO35` (pin 15) is the ESP32-P4 serial-bootloader strap, so a switch to ground on it is a chip that comes up in the ROM downloader whenever the button is held through a reset; `GPIO31` (pin 10) carries `CAM_PWR_EN`, and giving it away would cost idle power-down for the camera bank and the only route the P4 has to power-cycle a node that has stopped answering. `GPIO28` is not a strapping pin — 34 to 38 are — and the line it replaces has never been asserted: no flash board exists, `capture.c` only ever held the pin low, and `HWV_FLASH_EN_GPIO28` never left `UNVALIDATED`.

  So the built-in constant-current direct-flash assembly leaves D4-V1. A separate external flash module will be used later; it has no P4 pin in this revision and its interface is not chosen. `flashControl` stays `true` in `GET_CAPABILITIES` because the command surface exists, `flashHardware` stays `false` because no flash board is fitted, and no KDP surface changed. `BOARD_FLASH_EN` is `BOARD_GPIO_NONE`, the `_Static_assert` set follows, `HWV_FLASH_EN_GPIO28` stays in the registry as an append-only row that can no longer flip, and `buttons.c` earns `HWV_BTN_SHUTTER` on the first debounced press.

  The wiring is one part: a 6 × 6 × 4.3 mm tactile switch between JP1 pin 21 and GND on JP1 pin 6 or 16, with no external resistor and no capacitor. The P4's internal pull-up holds the pin high, the input is active low, and firmware does the 25 ms debounce and the 600 ms long press. On a meter against pin 6 the pin reads 3.3 V idle and 0 V held. Twelve header GPIOs still carry eleven signals: the four TX/RX pairs, `SYNC_OUT`, `CAM_PWR_EN` and `BTN_SHUTTER`. `BTN_FN` and the mode slide still have no pin and will not get one in this revision. ECN-0003.

- **Firmware 0.4.6: the node sweep no longer wears the shutter's lock.** Gate F left one refusal standing: `CAMERA_CAPTURE` answered `BUSY "A capture is already running"` with nothing running whenever it landed in the background node sweep, which took `capture_lock()` for its whole HELLO round (14 of 20 idle requests before the 300 ms absent-channel probe, 1 of 20 after, 5 of 41 under load). The wire never needed that lock - `cam_link.c` already holds one mutex per channel for exactly one request/response - what was missing was priority. `cam_sched.[ch]` is the policy, host-tested (1,198 checks, cases A-L): REAL CAPTURE > BACKGROUND PROBE. A probe begins only when no capture is admitted and its channel is free, else it is deferred and the sweep comes back; a capture is admitted whenever no capture is active - maintenance never makes it BUSY - and if one probe is on a wire at that instant it waits for that single bounded transaction (300 ms absent, milliseconds present, one 3000 ms transaction when a present node goes silent), then starts. Channels are four independent objects; a capture defers all four. `capture_lock()`/`unlock()` bind `capture_active`; `capture_fire()` waits on a semaphore the probe's end gives; the sweep asks `capture_probe_begin()` per channel and holds nothing between channels. Additive telemetry: `CAMERA_CAPTURE` `bench.probeWaitMs`, `GET_RUNTIME_STATS` `probesRun` / `probesDeferred` / `captureProbeWaits`. Bench result in `firmware/HARDWARE_VALIDATION.md` ("Shutter availability").

- **Firmware 0.4.6: the radio recovers from a C6 reset without a P4 reboot - ROLL-C test 3 passes.** Bench 2026-08-30 on 0.4.5 (`C6_RESET_BENCH`): the C6 rebooted cleanly, the P4 kept running, and the host side kept the state of a coprocessor that no longer existed; nothing re-established anything and only a P4 reboot brought the radio back. `radio_recovery.c` is the fix, a host-tested state machine (113 checks, cases A-M of the bench brief) the supervisor in `net_hosted.c` drives: detect (ESP-Hosted `TRANSPORT_FAILURE`, `sdio_link_up` false, or two unanswered liveness RPCs) → quiesce (stop wanting an association, tell the netif it is disconnected *and stopped*, ignore events, send no RPC into the dead coprocessor) → `esp_hosted_deinit()` → one enable-line pulse with bring-up's 20 ms → free the recovery reserve and `esp_hosted_init()` + `connect_to_slave()` → wait for `rx_ready`, then `rx_ready && tx_ready` (the transport proof, not init's return code) → the version RPC over the restored transport, same policy, incompatible parks → the stale remote Wi-Fi stack deinitialised over the live transport, then init/STA/start → stored credentials through `net_link` → an address the existing lease rules accept → `recoveries` +1 in `NETWORK_STATUS` and `upload_queue_network_restored()`, which makes every `RETRY_WAIT` job due now with its attempts kept and wakes the worker. Every wait bounded; failures back off 2 s doubling to 60 s and park after 6 with the reason on the record; each attempt is a generation and stale observations are ignored; a parked machine restarts only on a bench pulse.

  Six images to get there, each one measured: the deinit hung/panicked when an RPC had been sent into the dead slave first; in-place re-enumeration read every frame as ~979 KB because the component's byte counters reset only in its own deinit/init; the re-init then asserted on its 15,872 B SW_AGGR buffer because the P4's PSRAM heap carries no `MALLOC_CAP_DMA` and internal RAM was down to a 7 KiB largest block - so `kdp_server`'s two 16 KiB frame buffers moved to PSRAM and a **recovery reserve** of two 16 KiB internal DMA blocks is held from bring-up and freed the moment before re-init; finally lwip asserted `netif already added` until teardown also ran the netif's stop action. `GET_RUNTIME_STATS` gains `internalFreeKB`, `internalMinFreeKB`, `largestInternalDmaKB`. On the board: five consecutive recoveries without a reboot in 9.8-21.8 s (one 122.9 s, spent in the component's own deinit RPC timeouts), and ROLL-C test 3 passing end to end - `firmware/HARDWARE_VALIDATION.md`.

- **Firmware 0.4.6, Gate F: photography measured against the radio, and the two ways the upload queue could park a good photograph.** Bench 2026-08-30, single CAM1 (OV3660, 1600x1200), LAN backend, four images; the record is `firmware/HARDWARE_VALIDATION.md` ("Gate F - photography wins"). What changed in the firmware:
  - `capture_report_t` and the `CAMERA_CAPTURE` reply carry a `bench` object (additive): `sdWaitMs` (time from shutter to holding the card), `radioState`/`radioDetail`, `uploadActive`/`uploadPending`, `internalFreeKB`/`largestDmaKB` at the shutter, the storage lock's cumulative yield and timeout counts, the capture worker's stack low-water mark, per-frame `chunkRetries[]` and `crcMatch[]`. One snapshot per capture, no new log lines.
  - The node sweep in `main.c` holds `capture_lock` while it HELLOs every channel; the default 3000 ms per absent channel cost ~9 s of lock every ~19 s on a one-camera body and refused 14 of 20 `CAMERA_CAPTURE` requests at idle. An absent channel is now probed for 300 ms (`OFFLINE_PROBE_MS`, `camlink_hello_ch_timeout()`); a present node answers in milliseconds. After: 1 refusal in 20 at idle, 5 in 41 under Gate F load - the residual sweep window, still open, recorded.
  - An upload step that could not take the card because a capture holds it is a yield, not a failure: `RQ_DISP_YIELD` (appended to `rq_disposition_t`), `rq_classify_step()`, `roll_step_result_t.card_yielded`, `roll_http_file_size_ex()` / `roll_http_sha256_file_ex()` / `read_card_file_ex()`. It costs no attempt and waits `CARD_WAIT_MS`. Before, twelve refusals inside two shutters parked the photograph `FAILED` with "the asset is not on the card" (CAP_000231, stat refused) or "META.JSON unreadable on the card" (CAP_000253, register step) while the file sat intact on the card; and a parked job whose record could not be written was re-stepped past its budget (attempts 20 against 12). A settled job now stays settled. Host tests: roll-queue 1,138 checks (+325).
  - Known and left: `UPLOAD_QUEUE_RETRY` revives the parked jobs the RAM list holds (`PARKED_IN_RAM_MAX` 4) and the rescan brings the next parked records back as parked, so a card with many parked captures needs repeated presses; the `failed` figure read 35 after a press that uploaded four, then caught up over the next passes. Both are queue bookkeeping, not photography, and are recorded in the validation file.

- **Firmware 0.4.5: a bench-only way to reset the C6 and nothing else.** ROLL-C test 3 asks what the upload queue does when the radio chip reboots under it while the P4 keeps running, and no product path resets the C6 after boot. `C6_RESET_BENCH` (`0x4d`, in the diagnostics block, private) pulses the C6 enable line once with bring-up's own timing and reports the link down; it is compiled only with `-DKINO_C6_RESET_BENCH=1` on a radio build, and every other build answers `UNSUPPORTED_COMMAND` and moves no pin. The decision lives in `bench_c6.c`, host-tested (13 checks: one pulse when built in, nothing otherwise, never a P4 restart). The bench client now keeps the raw bytes of any reply that does not parse. What the C6 reset does to a pending upload is recorded in `firmware/HARDWARE_VALIDATION.md`, not claimed here.

- **Firmware 0.4.4: the first photographs reach a Roll on a real backend, and the two defects that stopped them.** The LAN bench (2026-08-30, D4 on Wi-Fi at 10.20.80.181, the repository's Fastify API on the dev PC at 10.20.99.57:3000 with Postgres, Redis, MinIO and the worker) put a capture through the whole chain for the first time: document POST 201, thumbnail asset first, original second, `/complete` 200, worker `extract-metadata` and `generate-gallery-still` done 130 ms and 280 ms later, one Postgres row on the Roll, and the object in MinIO byte-identical to `C1.JPG` on the card (SHA-256 `66493736…d4353b`, 72,108 B, CRC32 `64bb3d9a` on the card, in the object and in the API's `assets.sha256`). Two application defects had to go first.

  **A photograph did not know its Roll.** `meta.c` wrote `rollId: null` into every META.JSON, the capture path never told the upload queue about a finished capture (only UPLOAD_ENQUEUE did, and it used whatever Roll was current), and boot reconciliation stamped the current Roll onto every committed capture that had no record. On the bench card that was 102 captures with `rollId null` and 34 UPLOAD.JSON records all naming a Roll their photographs were never taken on. Now `capture_report_t` carries the backend `rollId` snapshotted at the shutter, META writes it (string, or `null` when the camera was not on a Roll), a capture-done listener enqueues with that id, `upload_queue_enqueue()` reads the Roll from META and refuses a capture that has none (`ESP_ERR_INVALID_STATE`; UPLOAD_ENQUEUE answers `INVALID_STATE`), and reconciliation compares the record's Roll with META's: a disagreement, or a record for a photograph whose META names no Roll, is **retired** (parked `FAILED`, `last_error` "no Roll provenance: capture …, record …") rather than uploaded. The 34 stale records on the bench card were parked that way; their photographs are untouched. `rq_reconcile_action()` gained `RQ_REC_RETIRE`; MEDIA_READ may return `UPLOAD.JSON` so a bench can back a queue up before it is touched.

  **A job resumed after a reboot waited on the previous boot's clock.** `next_attempt_ms` is a deadline on the boot's monotonic clock and the record keeps it; after a reset the resumed `RETRY_WAIT` job sat until the new uptime passed the old number - 27 minutes on the bench (CAP_000186, boot-412 to boot-413) while the API had been back for three. `rq_job_boot_resume()` voids the deadline on the RESUME path of `upload_store_inspect()`; attempts are kept. Host suites: 2,501 checks (roll-queue 806, meta 125, store 100, net-report 98, kdp_core 75, and the rest unchanged).

- **Firmware 0.4.3: a read-only audit of every firmware file, and the fixes that did not need a bench.** Seven auditors read the P4 app, the camera node, the C6 image, the UVC preview tool, the shared components, the host tests and the firmware documents (2026-08-29, issue #137). What follows is the part of the ~100 findings that is a correctness or boundary defect and can be verified by reading and by the host suite; the task watchdog, the partition table, the file splits, the KDP RX reader task and the C6 SDIO re-establishment loop each need bench time and are tracked separately.

  Two were critical. **DELETE did not delete.** `storage_capture_delete()` unlinked five names and `rmdir()`ed; every capture also writes `THUMB.JPG`, so the directory was never empty, the picture reappeared in the gallery with no metadata, and every aborted capture became a permanent "kept for inspection" orphan. The six names live in one table now, `STORAGE_CAPTURE_FILES`, read by the delete path and by the `MEDIA_*` allow-list so they cannot drift again. **Three of the six `MEDIA_*` handlers checked for `/` but not `..`**, while the other three checked both; `MEDIA_DELETE {"id":".."}` walked one level up and removed `/sdcard/KINO/C1..C4.JPG` and `META.JSON`. All six go through `pure_is_capture_dirname()`, the rule the network path already used.

  The rest, briefly. The TLS gate read a cached "clock untrusted" reason instead of the clock, so a clock set from Studio never released it and uploads idled for the whole boot; it asks `clock_trustworthy_for_tls()` now, and the hold release is one guarded operation instead of a read-then-write that could resurrect `IP_READY` after a disconnect. `net_link`'s state was written from four tasks and read from three with no lock; it has one, compiled out on the host so the tests still build. A dropped AP made the event task call `esp_wifi_connect()` from inside its own disconnect handler with no delay — a full-band scan loop; it is an `esp_timer` backoff, 1 s doubling to 30 s. `cam_probe` guarded twelve seconds of HELLOs with a try-lock sample and called it exclusion; it holds `capture_lock()` for the sweep. `ESP_ERROR_CHECK(camlink_init())` was the one abort in a boot written to degrade, and it fired before the USB recovery channel existed; it logs. The gallery read `META.JSON` into 1 KB when a two-frame document is ~1076 bytes, so every multi-camera capture would have rendered as a UUID with zero frames; 4 KB, with a host test that measures a four-frame document. The log-drain task blocked on the USB FIFO while holding the TX mutex; events use a 250 ms bounded write and count a drop rather than wedge the server. The soak test passed `jpegQuality` to the sensor unconverted, the D12 inversion again. The node's frame buffer was sized once at UXGA while QXGA was selectable, so a bright 2048×1536 JPEG over 384 000 bytes overflowed it; it is sized for QXGA. A capture could spend two 4 s `fb_get` timeouts on the node's only task against an 8 s host budget; the discard is gated on a queued frame and the host waits 12 s. `taskmon` published a slot before filling it and read the table unlocked, the use-after-free it was written to prevent; it publishes last and reads under the lock, and its registry was exactly full at 20. A stored `apiBase` over 47 characters was truncated into a different, still-valid URL and used with the bearer token; over-long values fall back to the compiled default. Physical buttons drove the renderer from the buttons task — dormant only because no pin is assigned; they post to a queue the UI task drains. Plus: NVS return codes on the capture counter, a short `fwrite` that left a truncated frame in a committed capture, a viewfinder hold shorter than the pump it waited for, control bytes from a server error body that could make `UPLOAD.JSON` unreadable forever, thirty-two parked uploads blocking every new one, a per-pixel divide in the viewfinder blit, and a click sound re-synthesised with two thousand `expf` calls and 33 KB of internal heap on every tap.

  Documents were wrong about the board. `firmware-contract/README.md` D13 said `FLASH_EN` had no GPIO (it is GPIO28, JP1 21) and gave `SYNC_OUT` two different pins in one section (GPIO32, JP1 19); `power.c` and `hardware_validation.h` still described the pre-ECN-0002 map, telling a reader the camera-rail switch was inert while the idle path drives it. `firmware/README.md` said nothing was bench-validated under a ledger with six validated rows. The three C6 documents disagreed on whether anything had run on a board; `HARDWARE_VALIDATION.md` owns that now and the prose points at it. The two recorded SHA-256s for the same `kino-c6.bin` still disagree, and that is written down as a disagreement for the next build to settle rather than a pick. `firmware/*/sdkconfig.debug` — referenced by name, untracked by omission — is committed. Host tests: `kdp_core` 46 → 75 checks with four new decoder cases (exact `KDP_MAX_PAYLOAD`, a decoder smaller than the frame, discard accounting, magic inside a payload); new cases for `net_link_clear_clock_hold`, `rq_sanitise_detail`, an escape-heavy `last_error` under the 768-byte record cap, and the META.JSON size bound.

- **Firmware 0.4.2: the capture path had four concurrency defects an audit could see and a bench could not yet.** `storage_file_crc32()` hashed through one `static` 4 KB buffer while four capture workers and the bench read files back at the same time, so one task's `fread` could land between another's `fread` and its CRC update — an intermittent "stored X, node said Y" on a card that kept every byte, or a false pass. The buffer is per call now. Product captures and the bench captures in `kdp_server` (`CAMERA_TEST`, soak, `STORAGE_SELF_TEST`, `STORAGE_BENCH`) held two different locks that never looked at each other; a node holds exactly one frame and a new capture command replaces it, so a bench capture on cam1 during a shutter capture turned the worker's next chunk read into `BAD_ID`. One lock, `capture_lock()` in `capture.c`, and a binary semaphore rather than a mutex because the soak job releases from a task that did not take it. The card lock moved from `capture_task()` into `capture_fire()` for the same reason the viewfinder hold did: `CAMERA_CAPTURE` calls `capture_fire()` directly and was writing four frames with nothing keeping the upload worker or a `MEDIA_READ` off the SDMMC bus; the six `MEDIA_*` handlers and the gallery tile decode take the card as the UI user now and answer `BUSY` rather than contend. The viewfinder's pump counter was a `volatile int` incremented by four unpinned tasks on a dual-core part — `volatile` stops the compiler caching it and nothing else — so a lost update could let a capture start while a preview transfer was still on the wire, or leave every shutter press waiting out a 1.5 s hold. It is `atomic_int`.

  Two more from the same audit. **The camera node now discards the queued frame before a photograph.** With `fb_count=1` the driver captures one frame the moment the buffer is returned and then stalls, so every capture after the first was handed a frame exposed just after the previous release — M1 measured 1.8 s, 3.4 s and 27.0 s before the shutter. `camsensor_discard_queued()` empties the buffer first, which bounds the frame start to one frame period after the command (~112 ms at UXGA); preview sizes skip it so the viewfinder keeps its rate, and the reply carries the cost as `discardMs`. This is a correctness fix, not synchronisation: the four sensors still free-run, and `SYNC_FEASIBILITY.md` still scopes that work. And **both images now build at `-O2`**: every one of the 1005 objects in the P4 image was compiling at IDF's default `-Og`, CRC loops and JPEG staging included. `sdkconfig.debug` is the overlay that puts `-Og` back for a debugger; a `sdkconfig` generated before this change keeps `-Og` until regenerated, and `firmware/README.md` says so. The first `-O2` build failed on `-Werror=stringop-truncation` and `-Werror=format-truncation`, which only fire with optimisation on: every `strncpy(dst, src, sizeof dst - 1)` in `p4/main` is `strlcpy` now (26 sites, five of them in the soak job with no `- 1` at all, which is the unterminated copy the warning exists for), and the Wi-Fi credential slot key grew from 8 to 12 bytes so `"n%u"` cannot truncate. The `-- USING O3` line in the configure output is ESP-IDF's own message, not a project flag; every object was `-Og` while it printed.

- The JP1 header map was wrong for the second time, and this time the board settled it. The previous entry replaced the recorded pinout with the manufacturer table for the `JC-ESP32P4-M3-DEV` — a different carrier that shares the ESP32-P4 module and nothing else, our board being the `JC4880P443C-I-W`. Under that map `CAM1` opened UART1 on GPIO1/GPIO2, which reach no connector here, so the camera link could not work and its failure looked exactly like a wiring fault: a node that was known good in isolation answered nothing across 113 frames, a diagnostic node image logging every byte on its link UART saw none, and a TX-to-RX loopback across JP1 7–9 with the node removed entirely received zero bytes while a continuity check on the same jumper read a clean logic 1.

  So the header was measured instead of transcribed. The P4 drove all 47 of its usable GPIOs in turn — everything except the console pair and the mounted card's six — each announcing its own index in binary as a six-pulse sync followed by six bit windows, one pulse for a 0 and three for a 1, while a camera node watched a single wire and reported what it counted. JP1 pin 13 answered as GPIO49; JP1 pin 7 answered as GPIO52, predicted from the drawing before the run. The map is back to GPIO52/51/50/49/35/34/32/28 on the left and GPIO33/31/30/29 on the right, which is what the repository recorded originally and could not justify at the time.

  Twelve header GPIOs carry eleven signals, so `FLASH_EN` (GPIO28) and `CAM_PWR_EN` (GPIO31) have pins again and the I²C expander the previous entry proposed for M2 is unnecessary — which matters for M1 §37, where cutting the camera bank is the whole test. `GPIO35` on pin 15 is the one spare, and it stays unconnected: it is the ESP32-P4's serial-bootloader strap, so a pin tied low there is a board that comes up in the ROM downloader instead of the application, which at a bench reads as dead firmware rather than as a wiring mistake. `GPIO34` carries `CAM3_TX` and is a strapping pin too, safe only because we drive it and a node's UART RX is high impedance; a camera's TX must never land on either. Both rules are now compile-time assertions.

  The rule that came out of it, and the reason this is the last time: do not edit these numbers from a datasheet, a photo of another board, or a vendor page. Measure the pin. A manufacturer document is evidence about *a* board; only the bench is evidence about *this* board. ECN-0002.
- **The D4 header map was fiction, and the camera UARTs were on pins that do not exist.** The repository recorded the Guition carrier's 2x13 expansion header as carrying GPIO52/51/50/49/35/34/32/28 down the left and GPIO33/31/30/29 down the right, and put the four camera UARTs on 52/51, 50/49, 34/33 and 30/29. The rows came in on 2026-08-21 as "hardware data" with no manufacturer source, and because rows 1-3 and the C6 block were right the table passed review. The JC-ESP32P4-M3-DEV pinout exposes exactly eleven P4 GPIOs on JP1 — 1, 2, 3, 4, 5, 20, 32, 33, 45, 46, 47 — and not one of the eight recorded camera pins is on any connector. A node wired to the old instructions could not have answered, and the failure would have read as a bad ground.

  GPIO3 and GPIO5 are the touch and panel resets, both validated on hardware, so nine header pins are free for ten wanted signals. The map is now CAM1 GPIO1/2 (JP1 pins 7/9), CAM2 GPIO47/46 (10/12), CAM3 GPIO32/33 (19/21), CAM4 GPIO45/4 (14/13), SYNC_OUT GPIO20 (17); FLASH_EN and CAM_PWR_EN have no header pin and are `BOARD_GPIO_NONE`, which the firmware honours by not driving them rather than by driving pin -1. None of the nine is a strapping pin (34-38), USB (24-27), SD (39-44), the C6 SDIO bus (14-19, EN 54), I2C, I2S or LCD. `board_d4v1.h` is the one source of truth: `_Static_assert`s prove uniqueness, header membership and column parity at compile time, a host test (`test-pins`, 293 checks) repeats them and dumps the map, and a vitest in `@kino/hardware-profiles` parses the header and fails if `d4-v1.json` drifts from it. The profile's gpio keys are `CAM1_TX`…`CAM4_RX` now, each with its JP1 pin. Every camera row in the validation ledger stays UNVALIDATED; the one row that had been marked validated, `CAM_PWR_EN GPIO31`, is void, because GPIO31 goes nowhere. Hardware design package 0.1.1, ECN-0001. Do not wire a XIAO from any document that names GPIO52/51.

- **The C6 routing is established, and finding it turned up a defect that was waiting for the bench.** The mapping came from outside the repository — Guition documentation for this carrier — and was reconciled against two sources inside the toolchain before any pin was written down. `espressif/esp_hosted` 3.0.6 pins all six SDIO signals to exactly GPIO14-19 for a P4 host with a C6 coprocessor, with `min == max` so it is one value rather than a range, and `ESP_HOSTED_HOST_RESET_GPIO` defaults to 54 for every P4 target rather than one board. Independent support that this carrier follows the reference pinout: the microSD block is exactly the P4's slot-0 IOMUX pad set from the SoC headers, and that set was already validated here by a real 29820 MB mount. CLK and CMD cross over between the two chips, which looks like a transcription error and is not.

  The defect was not a pin. Separate pins are not separate driver resources: the P4 has one SDMMC controller with two slots, `SDMMC_HOST_DEFAULT()` selects slot 1, and `storage.c` never assigned `.slot` — so the card has been sitting on the slot ESP-Hosted needs for the radio. It worked, because slot 1 is matrix-routable and the pins were passed explicitly, which is exactly why it would otherwise have been found at a bench with a half-built radio. The card is now on slot 0, where those six pins are the IOMUX pads the board wires; slot 1 has no IOMUX path at all, so the old configuration routed the card's own dedicated pads through the GPIO matrix to reach the wrong slot. Espressif ship this arrangement as an example. `GPIO54` is named `BOARD_C6_EN` and not `BOARD_C6_RESET`, because it is the C6's `CHIP_PU` — an enable — and a macro called `C6_RESET_HIGH()` asserts the opposite of what it reads like. Its polarity on this carrier is still unconfirmed, so it is one constant for the bench to flip.

- **The C6 image is Espressif's ESP-Hosted coprocessor now, not a bespoke Wi-Fi application.** The earlier conclusion that the official slave "does not compose as a component on IDF 5.5.1" was measured against esp_hosted **0.0.10**, a stale package; 3.0.6 resolves and carries the coprocessor firmware in the same component. So the hand-written radio app was wrong, and `radio.c`, `transport.c` and `board_c6.h` are deleted rather than kept because they existed — the component owns the radio, the RPC server and the SDIO slave, and its Kconfig declares *and enforces* the slave pins, so a duplicate set nothing included was only somewhere to drift. Pinned to an exact 3.0.6, because host and coprocessor negotiate an RPC wire version and a mismatch on this board presents as a transport fault, which is the failure most likely to be misdiagnosed as bad Wi-Fi. 1 105 872 bytes, and two clean builds of one commit match. The module's flash size is unknown and the image does not fit the 2 MB table, so that is a gate at the top of its README rather than a footnote.

- **Capture and upload share a real lock instead of a boolean.** The previous state was a file-static mutex in `capture.c` that nothing else could see, plus a flag the upload worker polled — a hint, not exclusion, so a reader that opened a handle between the check and the capture still took a descriptor. `storage.h` now owns the card with three users in priority order, a capture is never refused it, and the worker gives it back early when `storage_yield_requested()` goes true, which bounds a capture's wait by one chunk rather than one whole file. The audit that came out of this corrected the stated reason for the descriptor budget: **no path in this firmware holds two handles at once**, capture included, because the frame is closed before its CRC read-back opens it. The real reason a capture holds the card is the SDMMC bus and the frame spread, and three comments that said otherwise are fixed.

- **Two test suites were flaky for findable reasons, and the Twin build was red.** Three sites indexed a `Record<FirmwareProfileId, …>` with a plain `string`, which is a `TS7053` that breaks `tsc -b` and therefore `npm run build` in CI; one narrowing accessor fixes all three and keeps the hazard the casts would have hidden, since the lookup can genuinely miss. The worker's queue test waited for the `failed` row while asserting on the `abandoned` row written after it. The KDP relay test picked a port from a fixed 40-wide window with no bind retry, so a lingering socket surfaced as an unrelated timeout; it asks for port 0 now, which needed the relay to report the port it actually bound rather than the one it was asked for. Worth recording: local npm 9.6.4 exits **0** when a workspace script exits 7, while node 22's npm 10.9.8 — the one CI installs — returns 7. A green local `npm test` proves less than it looks like.

- The camera had two wall clocks and only one of them was ever set. `clock_set()` moved a private epoch base inside `clock.c`; `settimeofday()` was never called, so `klog`'s `t`, FAT's file dates and everything else reading `gettimeofday()` went on counting from power-on while `capturedAt` reported the host's date. The bring-up log caught it in the plainest form available: the entry announcing "clock set to 2026-08-27T19:38:44+02:00 by host" carried `t=526536`, about nine minutes past 1970. It also explains the 1970 dates that looked like a corrupt persisted clock and were not — the RTC keeps running across a soft reset, so those numbers were the board's accumulated powered time.

  KINO wall time is now the ESP-IDF system clock. `clock_set()` calls `settimeofday()` and persists, `clock_now_ms()` reads the system clock instead of keeping a second epoch, and `klog` asks `clock_now_ms()` rather than libc, so there is one definition of what time it is. `clockSource` and the UTC offset stay KINO metadata, because the system clock cannot hold either. `esp_timer_get_time()` is untouched and remains the monotonic clock for `klog.us` and every duration — a wall-clock correction must be free to jump and a measured duration must be free of it. `LogEntry.t` keeps its unit and meaning.

  Restoring gained the rule it never had: a persisted time is adopted only if it is a real time (2020..2100) and only if it is **later** than what the system clock already reads. The RTC survives a reset, so after a host sync the running clock is fresher than the NVS snapshot, and adopting the snapshot would date the next capture before one already on the card. `pure_clock_restore_action()` holds that decision so it is host-tested rather than reasoned about: 19 new checks, and a mutation to the old always-adopt behaviour fails exactly the two that describe the regression.
- `GET_RUNTIME_STATS` was reporting freed memory as a stack measurement. The icon builder deletes itself when it finishes and the task registry kept its handle, so every snapshot called `uxTaskGetStackHighWaterMark()` on a TCB that had been freed. On the first P4 bring-up it read 0, then 1460, then 1380 across three calls seconds apart — drifting, because the heap underneath was being reused, and 0 reads as a task that all but overflowed. A self-deleting task now hands the registry a last reading while its own stack still exists, and the row is marked `exited` so a boot-time number is not taken for live telemetry. Registration became idempotent by name and refuses to resurrect an exited slot, which is the half that actually made it work: the icon builder outranks the task that creates it, so it finishes and reports before the `xTaskCreate` site has registered it at all, and the registration arriving afterwards carried the dead handle. Measured after the fix: 2292 bytes, identical across four calls over 35 s.
- `cam_probe` had 356 bytes left of its 4096-byte stack, measured on the first P4 bring-up with no nodes fitted, while it was doing nothing but timing out on four empty channels. The branch it takes when a node *answers* is the expensive one — a `camlink_info_t` on this stack, filled through `camlink_get_info_ch()`, then a `klog` line through varargs — and it runs the instant CAM1 first replies. The overflow would have landed exactly on the node-greeting checkpoint and read as a link or node fault. 8192 now, and the same measurement reports 4452 free.

- Two clean builds of one commit produced different firmware, so a hash written into a bench record could not identify the source that produced it. `CONFIG_APP_REPRODUCIBLE_BUILD` was unset, which leaves ESP-IDF stamping the build clock into `esp_app_desc` and deriving the ELF SHA-256 beside it: two `fullclean` builds of identical `camnode` source differed in 67 bytes, beginning with three digits of the build time at 0x74 and the whole ELF SHA-256 field at 0xB0. The option is set for all three apps now, and `camnode` built twice from two different directories gives the same `kino-camnode.bin`. Nothing in this firmware calls `esp_app_get_description()`, so no timestamp is given up to do it. M1 identifies the flashed image by hash, and until now that record was decoration.

- The camera bench tool reaches its own log. Pressing BOOT during the three seconds after power-up — with the LED lit to mark the window — skips UVC, keeps the USB-Serial-JTAG port, redirects the log onto it and reports per-frame JPEG sizes with a SOI/EOI check done on the device, before USB touches the data. It could not be a single read at startup, which is what it was first: BOOT is GPIO0, so holding it while the board powers up puts the ROM into download mode and the app never runs. First use corrected three things guessed at earlier — the sensor implements every setter this firmware calls rather than lacking denoise, real JPEGs are 7.7-30.4 KB rather than the 160 KB the transfer buffer was sized for, and the sensor sustains at least 16 fps, so the 6 fps over USB is neither the clock nor the sensor. Bulk transfer was then tried against that and delivered 6.1 fps against 6.0, so both obvious levers are tested and 6 fps is what this component gives; it is kept for its packet retransmission rather than for a frame rate it did not buy.
- The six KDP questions the firmware contract listed as "firmware team decision required" are decided, because a bench is the wrong place to meet a design question. Sequence IDs wrap to 1 and never to 0 — 0 is the events' sentinel, and a uint32 left to overflow would start minting requests that read as events; `nextSeq()` in `packet.ts` and `kdp_next_seq()` in `protocol.h` are the same rule on both ends, and the P4’s link to the camera nodes now uses it. HELLO is confirmed **not** to be a precondition and firmware may not make it one: the client, the reference device and the P4 dispatcher already agree, and a stricter device would reject hosts that are within contract. `GET_MODES` and `CAMERA_ARM` get real response types — `armWindowMs` is required, since with no CAMERA_DISARM it is the only thing telling a host when the sensors fall back to `ready`. `STATUS` (0x81) and `FW_PROGRESS` (0x82) are reserved and must not be emitted by a 0.x device rather than being given a guessed payload for a flow that does not exist. Media resume stays offset-restart with the frame CRC as the per-chunk check and no completion hash. `JOB_PROGRESS` for a job this session never started is sanctioned for the reconnect case that produces it, and inventing job IDs is not. None of it bumps the protocol: KDP stays 1.
- The guest Roll is rebuilt as the album that belongs with the camera. Chrome is a moulded warm-grey plate — the ABS of a camera accessory, edged by two 1 px inset lines rather than a gradient — and the photography runs full-bleed on black between the plates, one capture per row on a phone. The frame counter sits in a dark window let into the plate the way it does on a camera's top deck, the three destinations are chunky keys in a routed well where the selected one reads as pressed in, and clock marks group the stream by minute instead of stamping a relative time under every tile. The four-frame mark is the wiggle's playhead: one bar per camera, and the lit bar is the frame on screen, so it says a capture has four frames, shows which one you are seeing, and is the indicator when motion is off. The photo page is back, photograph, contiguous four-frame strip, camera metadata, and one Save. Type is BIZ UDPGothic with tabular figures — 56 kB of Latin subsets; the Japanese subset is 1.3 MB and is deliberately not shipped. The host dashboard keeps its light treatment, separated by `data-surface` on `<body>`.
- Saving hands the file to the system share sheet where the browser supports it, so a photograph reaches Photos instead of Files: a plain download link does not reach the camera roll on iOS. Downloads remain the fallback, and the sheet now names what each row is for — original, wiggle as MP4, and the three crops — with sharing a link alongside them.

- Asking for better JPEG quality made the picture worse. `jpegQuality` is documented `60..95` across the contract and Studio's sliders, where higher is better; `esp32-camera` takes `5..63`, where **lower** is better, and the node clamps to it. Nothing converted between them, so 85 arrived as a request for 63 — the worst JPEG the sensor can make — and 95 did the same. Both numbers sit inside the other scale's range, so neither end could detect it. One conversion now, in `capture_quality_to_sensor()`.
- Only CAM1 was ever greeted. The probe task said hello to one channel, which was right while one node was all the harness had and stopped being right the moment a capture asked which cameras to fire: a channel nobody has greeted reports offline, so a body with four nodes wired would have taken a one-frame photograph and called three cameras missing. All four are greeted in turn now — in turn rather than at once, so a bench unit with one node fitted does not collect four simultaneous timeouts every two seconds.
- Every gallery listing reported every capture as a wiggle taken at the epoch. `media_summary()` read `kind` and `ts` from `META.JSON`, which has never contained either — it is a `kino.capture` document and always was, carrying `mode` and `capturedAt`. The fallbacks looked exactly like deliberate defaults. The wire names are unchanged; only the keys read from the file are.
- The conformance suite failed honest behaviour. `MEDIA_INFO` demanded exactly four files, which was true while every capture came from a body with four cameras wired and is not true of a partial capture — a state the capture pipeline reports on purpose. It now checks that the file count agrees with the capture's own `frameCount`, which catches a real defect a fixed 4 could not, and treats the deliberately-omitted `sha256` as absent rather than failed. `MEDIA_READ` gained a check that offsets actually seek: reading the same bytes from 0 and from 128 looks perfectly healthy until a client assembles a file out of pages and gets page one repeated.
- Touch stopped losing presses, and neither cause was in the touch driver. Sounds played straight from the UI task: `play_click()` opens the codec, queues the samples, waits for the DMA to clock them out and closes again — the best part of 200 ms during which the GT911 went unread, so presses were missed and releases arrived late or not at all. Sounds now go through a queue to their own task and the UI never waits on one; the queue drops rather than blocks, because a backlog of ticks finishing after the finger has gone is worse than a missing one. The second cause was `s_down` being cleared on a **single** failed read, on a bus the GT911 shares with the ES8311 — a codec transaction could return no points while the finger was still down, so presses let go of themselves mid-tap, worst of all exactly while a sound played. A release now needs three consecutive empty polls, 45 ms against the ~80 ms a real tap takes to lift. The point is also published as one 32-bit word rather than two `uint16_t`s, because the UI could read the new x with the old y and register a press on a tile the finger never crossed.
- A touch that wakes a sleeping screen wakes it and does nothing else. The backlight goes off but the UI keeps running and keeps hit-testing, so reaching into a bag for a camera whose display had timed out fired whatever tile the thumb landed on. The whole press is swallowed until the finger lifts.
- Every 3D model rendered mirrored left-to-right. The fix that turned the objects to face the camera negated x as well as z, on the theory that a lone z flip would mirror the image; a lone z flip is the standard right-to-left-handed conversion and mirrors nothing, while negating both is a half turn about Y, which really does. It survived for as long as every object was symmetric — the film canister's leader and the crate's letter A, both on the wrong side, are what exposed it.
- The 3D depth buffer collapsed. Depth was scaled by a fixed constant, which for a model at about 1.9 radii put every near surface at roughly −283000 before clamping, so everything in front landed on 0 — and since the test rejects equal depths, whichever part was built first won: the camera body hid all four of its lens barrels and the gallery cards hid the photographs printed on them. Near and far planes are now mapped onto the full 16-bit range per model, which is what lets the buffer separate two surfaces a fraction of a millimetre apart.
- The camera XCLK drops from 20 MHz to 16 MHz, which is a capture-integrity fix and not a tuning preference. At 20 MHz the OV3660 corrupted 77 of 160 frames (48%), each carrying a chroma-damaged band in a fixed ~12-pixel zone around x=498 — JPEG MCU column 31. At 16 MHz the same measurement over 200 frames gave 1 (0.5%). Corrupted JPEGs at 20 MHz are a known esp32-camera problem and the guidance is to avoid multiples of 10 MHz on this part. `camnode` reads the same constant from `board_xiao_s3.h`, so the product was set to corrupt roughly a third of its captures over the same DVP bus — silently, into a roll nobody is watching a preview of. The cost is capture throughput, which single stills barely spend; a corrupt still costs the photograph. The 0.5% residue is upstream, and the next lever is the OV3660 PCLK register fix rather than another clock change.
- Sensor tuning is applied rather than left to whatever the driver last wrote: gamma, black and white pixel correction, lens correction, AWB with its gain stage, DSP-assisted exposure and a capped gain. Untuned frames were flat, grey and speckled, which is what makes a good module look faulty. Saturation goes to **-2**, Espressif’s own value for this part, whose example notes these sensors ship over-saturated — lifting it instead amplified a slight green bias until grey shirts read olive (G +1.9% untuned, +12.0% lifted, +5.2% at -2). Every setter is null-checked: the driver only fills in the ones a sensor model implements, and calling a missing one panics before USB comes up, which presents as a board that enumerates as a serial port and never appears as a camera.
- Wiggle playback and the D4 frame strip no longer depend on `downloadsEnabled`. A host turning saving off used to freeze every photograph in the Roll and hide the four frames behind it; that flag now gates only what leaves the phone.
- Guest touch targets meet 44 px, including the back link on the photo page, which was a 167×14 px hit area and the only way back. The photo page has an `h1` naming the photograph — its only heading had been `h2 "D4 frames"`.
- Roll's shared control styling no longer out-specifies the surface it lands on. `button:not(.kino-button):not(.roll-tab):not(.action-link):not(.frame-thumb)` scored (0,4,1) and silently forced 30 px controls and a light gradient onto anything new; bare-button styling is now scoped to the host surface, with `.kino-button` still covering the design-system button everywhere.

- The on-device UI is rebuilt around the camera rather than around a launcher. The 2x3 menu stays and becomes the home screen: **MODE, LOOK, GALLERY, ROLL, SETTINGS, POWER**, each a large Windows 98 shell icon with a word under it. There is no SHOOT tile, because shooting is a hardware action - the physical shutter opens the viewfinder from the menu and takes the photograph from the viewfinder, and it fires from any screen. FLASH and STATUS are gone from the top level: flash is a cycling control on the viewfinder, one press per change, and the diagnostics STATUS carried moved into Settings. There is no global status strip either; a permanent SD/WIFI/ROLL bar across every screen is what a miniature PC looks like, so battery lives in the viewfinder and storage speaks up only when it is nearly gone.
- The viewfinder is four previews, Back, Flash and Battery, and nothing else. Frame rates, card capacity, link diagnostics, the mode readout and the on-screen shutter are all gone - they were engineering information competing with the photograph. Four 4:3 panes on a 5:3 panel leave a column of dead space down each side whatever you do, so the three controls live in those columns and the panes take the full height: 308x231 each, against 272x204 for the strips-above-and-below version, which is 49% more picture.
- Every control now writes the real configuration. MODE and FLASH used to mutate a local variable and nothing else, so the screens did not change what the camera did and the viewfinder - which reads the config - visibly disagreed with the screen you had just used. MODE offers WIGGLE and QUAD, which is what `SET_MODE` accepts; the BURST and SINGLE the old screen advertised were never implemented anywhere in the firmware. LOOK sets `colorMode` across the four quad slots, which is a real contract value that persists and is stamped into META.JSON, and says plainly that looks are applied on import rather than pretending the preview will change. Anything the hardware cannot do renders disabled with the reason - brightness ("The backlight on this body is on or off"), Wi-Fi and auto-upload ("Not fitted"), shut down ("Hold the power slide").
- Gallery is a photo browser instead of a dead end. Thumbnails are focusable and open a single photograph decoded at 520x390 through `thumb_load` rather than a 208 px tile blown up, and a capture can be deleted behind a confirmation. Captions are one short line - the mode, or "2 of 4" in red for a partial - with no filename, size or path.
- The menu icons are Windows 98 shell icons at their native 48 or 32 px, scaled by an exact integer factor with nearest neighbour and given a much lighter display emulation than the XP set had. That last part matters: these are pixel art with hand-placed dither, and the sharp-bilinear pass built for smooth-scaled artwork averaged the dither into mush. `scripts/bake-w98-icons.mjs` decodes the ICO/DIB directly - taking the deepest frame at the largest size, because these files carry a 16-colour and a 256-colour copy of the same drawing and the first directory entry is the flat one.
- Every setting a screen writes goes through `meta_patch_path`, which builds the nested patch `config_merge` expects. It lives in `meta.c` and is host-tested against the real cJSON because the first version dropped the first path segment - `body.sounds.ui` built `{"sounds":{"ui":...}}`, which merges into the config root perfectly happily and writes a key nothing reads. The screen would have looked right and the toggle would have moved.

### Added

- **The camera can hold a Roll, and every photograph it takes is durably queued for it.** What it still cannot do is send one. When this was first written the reason was that the repository recorded no P4-side pin for the C6 at all; that has since been resolved and the remaining reason is that nothing has been run on a board. `firmware/C6_HARDWARE_MAP.md` carries the routing and its evidence chain, `firmware/C6_BRINGUP.md` the order to bring it up in.
- Everything that does not need the radio was built and is host-tested — 1369 checks, up from 514. The upload queue is the part worth having: `UPLOAD.JSON` lives inside each capture's own folder, written to a temp name and renamed, the same metadata-last discipline that makes `META.JSON` the commit marker. One file per capture rather than one queue file, so a corrupt record costs one photograph instead of the queue, a job cannot outlive the capture it describes, and reconciliation is a directory scan rather than a cross-check between two files that can disagree. A job carries no image bytes — it names a UUID and every step re-reads the card, so there is nothing a reboot can lose, and re-reading is also exactly what a 422 `CHECKSUM_MISMATCH` asks for. Progress is a set of completion flags and never a byte offset: an offset would be a second source of truth about the server's state and would be wrong precisely when it mattered. The test that matters asserts the acceptance criterion directly — 50 captures queued with no network, carried across a reboot, then drained, each registering exactly once.
- The contract's two statements about 422 had to be reconciled rather than picked between. Its queue section groups 422 with the drop statuses, "do not retry the same bytes"; its error table says "re-read the file from SD and re-upload". Both hold: the prohibition is on the *same bytes*, and a fresh read of the card is the one thing that can fix a checksum mismatch. So 422 is a bounded re-read that parks rather than loops, and it deliberately does not touch the network attempt counter — a bad file must not slow every later upload for that job. 401 and 403 halt the whole queue instead of parking one job, because they fail every job identically and parking them one at a time walks the entire backlog into FAILED for something the user can fix in a minute.
- **`NETWORK: NOT FITTED` was wrong twice over and is gone.** The C6 *is* on the module; what is missing is the P4's route to it. A user reading "not fitted" goes looking for a component to add. The Connection screen now reports the two facts separately — `Radio: ESP32-C6`, `Link: Not routed` — the same split `flashControl` and `flashHardware` already use, and every value comes from `net_link` so the screen becomes correct on its own when the transport lands. Association is never reported as connected: `NET_WIFI_ASSOCIATED` shows "Getting address", because a camera that says connected while DNS would fail has lied to the user and to its own upload queue, and `net_link_can_upload()` accepts `IP_READY` alone for the same reason. There is no on-screen keyboard, on purpose — a passphrase entered on a 480×800 panel with no physical keys is worse than the USB path, and building a bad one to claim independence from Studio would be the wrong trade.
- The ROLL screen shows a Roll, its join QR, and what is waiting. It works with no radio, which is the part worth explaining: `PublishedRollJoinRequest` is documented as a server-published assignment written to the camera over `ROLL_JOIN`, carrying an already-resolved `rollId`, `slug` and `guestUrl`. Studio is the party with an internet connection, so it creates or looks up the Roll against the real API and hands the camera the answer over USB-C. The camera persists that across reboot, renders the QR, and queues every capture against it — so a guest at a party can scan the camera's screen and be on the Roll while the radio question is still open, and when the transport does come up the backlog drains into a Roll that already exists and already has guests on it. `ROLL_CREATE` and the slug-only form of `ROLL_JOIN` are HTTP calls the camera cannot make and refuse with `NETWORK_UNAVAILABLE` naming the actual radio state; there is no CREATE button on the screen, because a control that cannot work is the same defect as a shutter that logged instead of capturing.
- Wi-Fi passphrases and the device token live in NVS namespaces of their own — `kino_wifi`, `kino_roll`, `kino_rollsec` — none of which is the `kino` namespace `config_store.c` owns and `GET_CONFIG` returns verbatim. That is a structural guarantee rather than a filter: there is no code path from a config reply to a passphrase, so the leak cannot be reintroduced by someone adding a field, whereas a redaction list would have to be maintained forever and would fail the first time it was forgotten. `NETWORK_LIST` reports the mask and `hasPassword`, never the passphrase, and the only way a secret leaves either store is a callback that hands it to its consumer and `memset`s the buffer before returning, so exactly one frame ever holds it. The `kdt_` token form, `Bearer`, `password=`, `token=` and `passphrase=` are stripped from every error string that can reach a KDP reply, `GET_LOGS` or a crash dump. Not protected, and recorded rather than implied away: `CONFIG_NVS_ENCRYPTION` is off, so a passphrase is plaintext in flash to anyone who can read the chip — the threat handled here is accidental disclosure through the protocol, the logs and the backups, which is the one that happens by itself.
- `FW_QUERY` answers, and `TargetId` gained `c6`. The D4 carries six firmware images and the version model could name five, so a C6 running a stale hosted image — a second thing that can be out of date in the field — could not be diagnosed. Every other command in the `FW_*` group still fails closed: there is one `factory` partition and no OTA pair, and a query is not an update path. Two conventions the response establishes: an empty `version` means the device could not read one and is not version zero, and an unreachable target is `idle` rather than `error`, because nothing failed and nothing was attempted.
- Uploads yield to photography rather than sharing with it. The worker runs at priority 2, below the UI at 4 and the capture workers at 5, and stops touching the card entirely while a capture is in flight. That is not only about CPU: the FAT volume is mounted with `max_files = 4` and a capture already holds a frame handle plus a read-back handle for its CRC check, so an upload reader competing for a handle would fail outright, and one reading the card during a four-camera transfer competes for the SDMMC bus the capture's timing budget depends on. Yielding costs an upload a few seconds; not yielding costs frames. Gate F has to measure it and has not.
- CI gained the C6 image, the two new host-test suites, and a reproducibility job. `CONFIG_APP_REPRODUCIBLE_BUILD` had been set for all three apps and the property was checked by hand once, but nothing enforced it afterwards — an unpinned dependency or a timestamp reaching the image breaks it silently, and the first place that hurts is an update whose hash does not match what was published. Two clean builds of the P4 and the C6 are now compared on every run.
- `GET_CAPABILITIES` still reports `network: false`, `roll: false` and `rollUpload: false`, and that is deliberate with the whole `0xa0..0xaa` surface implemented. Studio's `supports()` gate is fail-closed, so setting them true would make Studio render the Roll and Network pages and issue commands that must then refuse — a broken panel instead of an absent one. What the handlers buy in the meantime is not the flag: it is that a host gets a specific `NETWORK_UNAVAILABLE` naming the radio state instead of an `UNSUPPORTED_COMMAND` that cannot tell an unimplemented command from an unrouted chip. The new `radioFitted` and `radioRouted` carry the distinction until then.

- **The camera takes photographs.** One press captured nothing: `SHOOT` logged "no capture pipeline in this build" and that was the whole of it. `capture.c` now fires every online camera, writes `C1..C4.JPG` and a `META.JSON` into one folder under one UUID, and verifies each frame twice — the transfer against the node's own CRC-32, then the stored file read back off the card, because a link that delivered the bytes intact and a card that kept them are different claims. The frames are fetched concurrently, one worker per camera: the node link runs at about 92 KB/s and a UXGA JPEG is 200-400 KB, so four cameras in turn would be twelve seconds and the last frame would be a different moment, a different pose and possibly a different room. Done at once the capture costs about what one frame costs. A camera that fails costs you that camera and nothing else — the capture commits `partial` with a per-camera reason, because a dead CAM3 must not lose CAM1, CAM2 and CAM4. `META.JSON` is a `kino.capture` v1 document, the schema Studio already validates, so a card read on a laptop needs no reverse engineering. Wired to the on-screen key, the physical button and `CAMERA_CAPTURE` alike, and it emits `EVT_CAPTURE`.
- The shared trigger wire is driven — `GPIO32` pulses 200 µs at the start of every capture — and it coordinates nothing yet, which is recorded rather than glossed. The camera nodes still expose when their command arrives over their own UART, so the frames are separated by however long it takes to wake four workers and put four commands on four UARTs; that figure is reported as `dispatchSpreadUs`, under its own name. All three skews in `kino.capture.timing` stay `null` with a reason. `CAMERA_CAPTURE` with `action: "timing-test"` is refused rather than answered: a rolling shutter that free-runs has no fixed relationship between when a command arrived and when light was integrated, and microseconds invented here would be filed as evidence. Driving the pin now means the node-side arm is later a node change alone.
- `MEDIA_READ` and `MEDIA_THUMB` return bytes, so pixels can leave the camera at all — `MEDIA_LIST` had been offering names and sizes for files no host could fetch, which is why `gallery` was false. Raw bytes with the binary flag, not base64: a 300 KB JPEG through base64 costs a third again in transfer for nothing. `MEDIA_THUMB` pages exactly like `MEDIA_READ` on both the device and the reference mock, because a thumbnail is small but not bounded and a noisy frame can encode past `MAX_PAYLOAD` — a reply that silently did not fit would reach a client as a truncated JPEG rather than as an error.
- Every capture writes a `THUMB.JPG` beside its frames, made once from the frame already in memory rather than on demand from the card. The whole path is hardware — the JPEG codec decodes, the PPA scales, the codec encodes again — which is single-digit milliseconds against roughly a second in software, and that is the difference between a shutter that feels immediate and one that does not. The PPA scales in sixteenths, so a 1600-wide frame reduces by 3/16 to 300×225 rather than to a round 320: rounding up would overflow the box, and resampling afterwards would spend a second of CPU making a 320-pixel picture out of a 300-pixel one.
- The gallery screen shows the pictures instead of the card's statistics. Six 4:3 tiles a page, decoded on a task of their own — a page is six card reads and six JPEG decodes, and doing that inside a draw call would stall the screen for most of a second every time someone scrolled, while the screen is what tells them the camera has not hung. Tiles are 4:3 because every sensor on this camera is, and a tile of any other shape puts a black border down the side of every photograph it will ever hold. Chevrons sit in the margins where the page-turn taps are, drawn only in the direction that has a page. An empty grid says which nothing it is — no card, a card that would not mount, or a card with no captures — because a broken card and an empty one look identical otherwise. This is the only consumer standing next to the card, which makes it the only check that a capture is an image rather than a folder of the right size.
- A clock, and an honest account of what it is worth. The body has no RTC, no battery-backed clock and no network, and `kino.capture` requires `capturedAt`. `HELLO` gained two optional additive fields so a host can set the time, and every timestamp travels with a `clockSource` of `host`, `persisted` or `unset` — because a camera that has never been told the time must not invent a plausible date. A plausible wrong timestamp survives import, sorts into the wrong place in someone's roll and is never questioned again; an obviously wrong one is caught the first time anyone looks. A persisted time assumes no time passed while the camera was off, which is certainly wrong and deliberately so: it is the only assumption that cannot date a capture earlier than one taken before the power cycle. Host times outside 2020-2100 are refused, which is what a seconds-for-milliseconds mix-up looks like.
- The camera's screen is a four-lens viewfinder, which is what a four-lens body's screen is for — the six-tile launcher moved behind a MENU key. Two things had to change before it could exist at all. camnode accepted only `1600x1200` and `2048x1536`, both full-size stills at 7.7–30.4 KB, which is about 330 ms of link time each and would have made a four-up view a slideshow at under 1 fps; it now also accepts `640x480`, `320x240` and `160x120`, deliberately **not** on the KDP `Resolution` type, because a capture must never be stored at one. And `cam_link.c` drove a single UART with every piece of its state — mutex, decoder, counters, sequence — as a module global; it is now four independent channels, because the P4 has five high-power UARTs and each camera has its own, so four transfers overlap instead of queueing. That is the whole difference between a viewfinder and a slideshow, and it shows on the bench: with nothing wired, all four channels report their timeout within one millisecond of each other rather than eight seconds apart. Decoding is the P4's hardware JPEG engine — four software JPEG streams would cost more CPU than the link costs bandwidth. Panes with no node say `NO LINK` rather than showing a black rectangle that could mean any of several things, and the viewfinder only asks for frames while it is the screen being looked at.
- Timeout budgets are now per-caller rather than per-command. A stored capture may fairly wait eight seconds for a slow node — it is the photograph. A viewfinder pane may not: freezing the picture someone is framing with for eight seconds is worse than admitting it has nothing, and the next frame is 200 ms away regardless. Preview capture waits 900 ms and preview read 600 ms.
- Repeated link timeouts are counted instead of printed. An absent node is a permanent condition and the viewfinder asks each camera for a frame several times a second, so an unwired channel produced roughly three log lines a second forever — filling the ring and burying everything that mattered. The first failure keeps its full per-request detail, because that is the one that diagnoses the fault; repeats are summarised as a run length on the next line after thirty seconds, and a node that comes back logs its recovery. Measured with four dead UARTs: eight lines a minute instead of a hundred and eighty, with `run 64` still saying how fast they are failing.
- Physical controls, with no pins invented for them. `docs/HARDWARE.md` says outright that button and mode-slide pins are unassigned, so `BOARD_BTN_SHUTTER` and `BOARD_BTN_FN` are `BOARD_BTN_NONE` and skipped at init — a floating input read as a button fires the shutter by itself in a bag, which costs a roll and a battery, and that is a far worse failure than a control that does nothing. Assigning a real pin is a one-line change. The physical shutter and the on-screen key run the same `fire_shutter()`, because two ways to fire one shutter must not become two implementations of it. Unlike a touch, a button press is not swallowed when it wakes a dark screen: someone pressing a physical shutter means to take a picture whether or not they can see the panel.
- The camera has its own screen. A 480×800 ST7701S over MIPI-DSI, driven as a landscape 800×480 canvas through the P4's Pixel-Processing Accelerator: the CPU draws into linear memory and the PPA rotates and alpha-blends whole frames in hardware. Doing the quarter turn in the drawing primitives instead — writing each logical row down a column of the panel buffer — costs a 960-byte stride per pixel in PSRAM, a cache miss per pixel, and a renderer that cannot animate; the boot dissolve went from roughly 5–8 fps to a measured 26 frames in 452 ms, which is panel rate. Two framebuffers, because `draw_bitmap` recognises its own buffer and switches the scan source rather than copying, so presenting a frame is a cache write-back and a pointer swap instead of a 768 kB copy into memory the display is reading. Animation is driven by the clock rather than a frame counter, so a slow frame costs smoothness and never timing. Six destinations behind a boot iris that opens onto the wordmark; presses activate on release, so a finger that lands on the wrong tile can be slid off it.
- On-device power management, implementing the `BodyConfig` contract rather than inventing a scheme: `sleepS` blanks the backlight and `camIdleTimeoutS` drops the camera bank on `CAM_PWR_EN`, so four idle XIAOs stop costing a 3000 mAh cell anything. Thresholds are re-read every pass, so a Studio change takes effect immediately instead of after a reboot. Touch feeds the idle timer and KDP traffic deliberately does not — Studio polling status every second would otherwise keep the panel lit in a bag.
- `GET_POWER_STATUS`, `GET_CONFIG`, `SET_CONFIG`, `SAVE_CONFIG`, `RESET_CONFIG`, `GET_MODES`, `SET_MODE`, and the read side of the gallery: `MEDIA_LIST`, `MEDIA_INFO`, `MEDIA_DELETE`, `MEDIA_FAVORITE`. ### Known incomplete work

- **The D4 menu icons are Microsoft's and KINO holds no licence to them.** `REUSE.toml` declares all of `firmware/**` MIT, which would have relabelled the artwork as ours to give away; `firmware/p4/main/icons_w98.h` is now mapped to `LicenseRef-Microsoft-Proprietary` instead, and `license:check` fails if either that mapping, the header's own SPDX line or the `THIRD_PARTY_NOTICES.md` entry goes missing. The annotation records the ownership and grants nothing: a firmware binary built from this tree embeds the artwork, publishing that binary is redistribution, and scaling by an integer factor does not make it a new work. Issue #134 has to be answered — a licence, or original artwork in the same idiom — before a release carries these files.
- The D4 firmware in `firmware/` is CI-built but bench validation on physical hardware is pending; final hardware measurements are not recorded yet.
- Firmware signing and rollback are not implemented.
- Mobile-device browser acceptance (iOS Safari, Android Chrome) is device-gated and unrecorded.
