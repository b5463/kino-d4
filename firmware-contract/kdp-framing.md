# KDP framing

Byte-level contract. Extracted from `packages/kdp/src/protocol/packet.ts` and `crc32.ts`; every
number and hex dump below was generated by running that code.

## Transport

KDP is transport-independent. It assumes only a bidirectional byte stream with no message boundaries.

The V1 transport is Web Serial over USB. Port settings from
`packages/kdp/src/transport/SerialTransport.ts`:

| Setting | Value |
|---|---|
| Baud rate | 921600 |
| Data bits | 8 |
| Stop bits | 1 |
| Parity | none |
| Flow control | none |
| Host read buffer | 65536 |

Note this is the **host↔P4 USB link**. The P4↔XIAO camera UARTs are a separate bus with their own
baud, reported by `GET_CAPABILITIES` as `limits.currentUartBaud` and switchable with `SET_LINK_BAUD`.

## Frame layout

Little-endian throughout. Fixed 14-byte header, variable payload, 4-byte trailing CRC.

| Offset | Field | Width | Type | Value |
|---:|---|---:|---|---|
| 0 | `MAGIC0` | 1 | uint8 | `0x4b` (`'K'`) |
| 1 | `MAGIC1` | 1 | uint8 | `0x49` (`'I'`) |
| 2 | `VERSION` | 1 | uint8 | `PROTOCOL_VERSION`, currently `1` |
| 3 | `TYPE` | 1 | uint8 | A `Cmd` value on a request, the echoed `Cmd` on a response, an `Evt` value on an event |
| 4 | `FLAGS` | 1 | uint8 | `FrameFlags` bitmask, see below |
| 5 | `RESERVED` | 1 | uint8 | Encoder writes `0`. Decoder ignores it |
| 6 | `SEQUENCE` | 4 | uint32 LE | Request sequence ID; echoed on the response |
| 10 | `PAYLOAD_LEN` | 4 | uint32 LE | Byte length of `PAYLOAD` |
| 14 | `PAYLOAD` | `PAYLOAD_LEN` | bytes | UTF-8 JSON, or raw bytes when `BINARY` is set |
| 14 + `PAYLOAD_LEN` | `CRC32` | 4 | uint32 LE | See CRC below |

Derived constants (`packet.ts`):

```
HEADER_LEN  = 14
CRC_LEN     = 4
MAX_PAYLOAD = 16384
```

Total frame size = `14 + PAYLOAD_LEN + 4`. Minimum frame (empty payload) = **18 bytes**.

This layout is byte-identical to spec 04§3's recommended packet. `MAX_PAYLOAD` is not — see
[README D7](README.md#d7--payload-cap-is-16384-not-4096).

## CRC

CRC-32, IEEE 802.3, reflected, polynomial `0xEDB88320`, init `0xFFFFFFFF`, final XOR `0xFFFFFFFF`.
This is exactly ESP-IDF's `crc32_le()`, which is what the P4 firmware already has.

**Coverage: the header and the payload — bytes `[0, 14 + PAYLOAD_LEN)` — including the magic and the
`RESERVED` byte.** The CRC field itself is not covered.

Stored little-endian at offset `14 + PAYLOAD_LEN`.

## Flags

`FrameFlags` from `commands.ts`. A bitmask, not an enum of exclusive states.

| Flag | Value | Meaning |
|---|---:|---|
| `NONE` | `0x00` | Host→device request with a JSON payload |
| `RESPONSE` | `0x01` | This frame answers a request; `SEQUENCE` echoes that request's |
| `EVENT` | `0x02` | Unsolicited device→host frame; `TYPE` is an `Evt` value |
| `ERROR` | `0x04` | The payload is a `{code, message}` NACK. Always combined with `RESPONSE` |
| `BINARY` | `0x08` | The payload is raw bytes, not JSON |

Combinations the reference device actually sends:

| Bits | Value | Frame |
|---|---:|---|
| `RESPONSE` | `0x01` | Normal JSON reply |
| `RESPONSE \| ERROR` | `0x05` | NACK |
| `RESPONSE \| BINARY` | `0x09` | Binary reply (preview JPEG, thumbnail, media/sound read) |
| `EVENT` | `0x02` | Any `Evt` frame |
| `NONE` | `0x00` | Host request, JSON payload |
| `BINARY` | `0x08` | Host request, raw payload (`FW_CHUNK`, `SOUND_CHUNK`) |

Two hard rules the client's dispatch order imposes:

1. **Never set `EVENT` and `RESPONSE` on the same frame.** `KinoProtocolClient.handleFrame` tests
   `EVENT` first and returns; a frame with both is delivered as an event and the pending request
   times out.
2. **`ERROR` without `RESPONSE` is dropped silently.** The error branch lives inside the `RESPONSE`
   branch. A bare `ERROR` frame reaches nothing.

## Sequence IDs

- The host allocates `SEQUENCE`, starting at `1` per connection and incrementing per request.
- A response **must** echo the request's `SEQUENCE` in the header. Routing is by sequence alone —
  the client does not check that the response `TYPE` matches the request's.
- A response whose sequence matches no pending request is dropped silently. This is the normal fate
  of a reply that arrives after the host already timed out.
- Events carry no meaningful sequence. The reference device writes `0`. The client ignores the field
  on event frames entirely. **Do not try to correlate an event to a request through `SEQUENCE`** —
  for jobs, the `jobId` in the payload is the only routing key (04§16).
- Wraparound behavior is unspecified; see [README, unspecified item 2](README.md#unspecified--firmware-team-decision-required).

## Payload

### JSON payloads

UTF-8 encoded `JSON.stringify` output. No trailing NUL, no length prefix inside the payload — the
header's `PAYLOAD_LEN` is the only length.

Encoder/decoder edge cases from `packet.ts`:

- A request with no payload is encoded as `{}` (2 bytes), not as zero bytes.
- A **received** payload of zero length decodes to `{}`. So a device may answer a fire-and-forget
  command with an empty payload and the host reads it as an empty object.

### Binary payloads

Sent with the `BINARY` flag. Two shapes exist:

- **Device→host**: the payload is the file bytes with no header (`CAMERA_PREVIEW`, `MEDIA_THUMB`,
  `MEDIA_READ`, `SOUND_READ`).
- **Host→device**: `FW_CHUNK` and `SOUND_CHUNK` prefix an 8-byte little-endian header:

  | Offset | Field | Type |
  |---:|---|---|
  | 0 | `sessionId` | uint32 LE |
  | 4 | `offset` | uint32 LE |
  | 8 | data | bytes |

  Both are answered with a **JSON** response (`{ok, received}`), not a binary one.

### Size limits

| Limit | Value | Source |
|---|---:|---|
| Decoder hard cap on `PAYLOAD_LEN` | 16384 | `MAX_PAYLOAD`, `packet.ts` |
| Firmware chunk size negotiated by `FW_BEGIN` | 8192 | reference mock `handleFwBegin` |
| Sound chunk size negotiated by `SOUND_BEGIN` | 8192 | reference mock `handleSound` |
| `MEDIA_READ` / `SOUND_READ` response cap | 8192 | reference mock clamps `length` |
| `MEDIA_LIST` page size cap | 100 items | reference mock; also `limits.maxGalleryPageSize` |

A frame declaring `PAYLOAD_LEN > 16384` is not merely rejected — it triggers a resync (below). Do not
emit one.

## Decoder requirements

The decoder is a byte-stream state machine. It never assumes one read equals one frame. Firmware's
decoder must satisfy the same requirements (04§3), and the host-side implementation in `FrameDecoder`
is the reference for all of them.

04§3 lists five bullets — scan magic, tolerate boot spew, tolerate split/coalesced frames, reject CRC
failures, resync without reset. The first two are one behavior in any real implementation (scanning
for the magic *is* how boot spew is tolerated), so they are grouped below into four sections.

### 1. Scan for magic; tolerate boot spew

Bytes before the first `0x4b 0x49` pair are discarded and counted as a resync. An ESP32 printing its
ROM banner into the same UART is the normal case, not an error.

When no magic is found in the buffer, everything is dropped **except a trailing `0x4b`**, which may
be the first half of a magic split across two reads.

### 2. Tolerate split and coalesced frames

- One frame arriving as many reads: the decoder buffers until `14 + PAYLOAD_LEN + 4` bytes are
  available from the magic, then emits.
- Many frames arriving as one read: `push()` returns **every** complete frame found, in order. A
  caller that only handles the first return value loses frames.

Verified against the real decoder: a 75-byte frame fed one byte at a time yields exactly one frame
with zero resyncs; 25 bytes of boot spew followed by two back-to-back copies of that frame in a
single `push()` yields two frames and one resync.

### 3. Reject CRC failures

Computed CRC ≠ stored CRC → the frame is dropped, `crcFailures` and `resyncs` both increment, and
scanning resumes at `start + 2` (just past the magic that led into the bad frame). The magic itself
is not re-matched, so a corrupt frame cannot loop.

### 4. Resync without reset

Three conditions resync, all by advancing the scan position past the offending magic and continuing
in the same call — never by clearing the buffer or dropping the connection:

| Condition | Action |
|---|---|
| Bytes before magic | Discard them, count a resync |
| `PAYLOAD_LEN > MAX_PAYLOAD` | Skip past the magic (`start + 2`) and rescan. A garbled length field cannot stall the stream waiting for bytes that will never come |
| CRC mismatch | Skip past the magic and rescan |

`FrameDecoder` also exposes counters — `frames`, `crcFailures`, `resyncs`, `discardedBytes` — which
Studio surfaces in the protocol monitor. Firmware should keep equivalent counters; `GET_RUNTIME_STATS`
reports them as `protocol.droppedPackets` / `protocol.crcFailures`.

### What the decoder does *not* do

- It does not validate the `VERSION` byte. A frame with any version decodes and is dispatched. The
  reference **device** does check inbound version and NACKs `BAD_VERSION`; firmware should do the same.
- It does not validate `TYPE` against the known enums. An unknown event id decodes to a frame with no
  registered handler and is discarded.
- It does not inspect `RESERVED`.

## Worked example

`HELLO` request, sequence 1, from the real encoder.

Payload (57 bytes of UTF-8 JSON):

```json
{"protocolMin":1,"protocolMax":1,"nonce":1,"client":null}
```

Complete frame, 75 bytes:

```
                   V  T  F  R  seq---------  len---------
HEADER : 4b 49    01 01 00 00  01 00 00 00   39 00 00 00
PAYLOAD: 7b 22 70 72 6f 74 6f 63 6f 6c 4d 69 6e 22 3a 31
         2c 22 70 72 6f 74 6f 63 6f 6c 4d 61 78 22 3a 31
         2c 22 6e 6f 6e 63 65 22 3a 31 2c 22 63 6c 69 65
         6e 74 22 3a 6e 75 6c 6c 7d
CRC32  : 86 dd 9b 14
```

Reading the header: magic `4b 49`; version `01`; type `01` = `Cmd.HELLO`; flags `00` = `NONE`;
reserved `00`; sequence `01 00 00 00` = 1; payload length `39 00 00 00` = 0x39 = 57. CRC `14 9bdd86`
in host order, stored LE.

Minimum-size frame — `SAVE_CONFIG` (0x12) with an empty payload, sequence 7, 18 bytes:

```
4b 49 01 12 00 00 07 00 00 00 00 00 00 00 e4 16 d8 82
```

Use both as decoder fixtures. If firmware's CRC over these bytes does not produce `0x149bdd86` and
`0x82d816e4`, the CRC implementation is wrong before anything else is tested.
